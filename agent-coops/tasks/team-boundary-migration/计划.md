## 产品设计

Config 维护基础 Claude/Codex 配置、通用操作与沟通原则、基础安装及 Dashboard。Team 维护团队规则、workflow、宿主适配和独立安装。Config 只引用 Team 入口，不复制维护其私有实现。

本仓改动必须达到以下结果：

- 基础安装不再自动启用或管理团队能力，保留基础原则链接及既有团队配置。
- Claude 原模型选择语义保持。团队流程改为引用项目当前有效合同；合并验收不再强制使用已经冻结的全局 VERIFY。
- 旧发行及旧适配程序保留原字节，其他项目的版本、绑定和运行状态不变。
- TODO、VERIFY 保存原文、状态和证据。逐项迁移并读回后冻结；当前状态进入项目飞书任务。
- Config 在本次明确授权内接入 Team 0.2.1。接入先满足双端 loader 前置条件，再使用真实角色发布及候选检查。

[产品前后原型](evidence/config-product-prototype.html)只解释边界变化。本次不实现生产 `site/workflow.html` 的最终迁移指针；该文件由后续真实 Hermes Web 指南子目标交付。本仓通过不能替代主任务、实际部署或用户验收。

## 架构设计

### 模块与修改前后

| 模块 | 原行为或现状 | 目标行为 |
| --- | --- | --- |
| `install.sh`、`install.ps1` | 基础安装包含团队安装职责 | 基础安装只处理基础资源；Codex 基础 AGENTS 链接保留 |
| `scripts/install-workflow.py` 和旧安装参数 | 原入口具有团队安装或回退动作 | 只显示 Team 迁移说明；不写宿主文件、不下载代码；保留旧回执及备份 |

### 基础安装与兼容入口

复用现有安装器，不新增包装安装器或后台服务。Bash 的 `--workflow-only`、PowerShell 的 `-WorkflowOnly` 和 Python 兼容入口在任何宿主写入前返回迁移说明。基础安装路径继续维护 Claude/Codex 基础链接、既有备份方式和原本声明的基础插件行为。本次不增加插件安装，不调用 Team 安装器，不拉取私有仓库。

manifest 移除团队资源只表示本仓不再管理这些资源。实现和测试都必须证明已有 hook、Hermes 插件、来源登记、Profile 内容和旧安装回执仍保留。不能用删除这些文件来得到“没有团队受管项”的结果。

`codex/tests/test_workflow_install.py` 复用临时 HOME 测试基础安装与兼容入口。Hermes 原生测试改用临时插件 fixture，不再借用已退出安装职责的兼容入口；被测旧适配程序保持冻结。

### 基础原则与冻结资产

`claude/configs/CLAUDE.md` 保留原模型语义：子 Agent 显式设置 model；主代理使用 opus；常规成员使用 sonnet；复杂工作使用 opus；不使用 haiku。将这组要求归入基础模型选择说明。文件存在核对等通用要求保留。团队权限、阶段安排和确认点引用 Team 当前合同，不新增 Claude 团队适配器。

本项目主分支合并仍要求相关用户验收完成。验收正本改为本项目飞书任务，旧项目继续使用其原有效正本，不能把历史 VERIFY 的冻结误解为免除用户验收。未验收变化仍先进入 dev。

冻结集合为四个旧 workflow 发行目录、`codex/hooks/workflow-hook.py`、`hermes/workflow-plugin/__init__.py` 和 `hermes/workflow-plugin/plugin.yaml`。本轮只读核对 40 个文件，与候选基线 `819bbc4a1ad98b9fb657294806e1b06a1b269ebd` 完全一致。它们不属于可改实现范围。冻结说明和适配器 README 可以更新归属，但不能改程序、模板或旧发行摘要来消除兼容错误。

### 历史条目与在办任务

TODO、VERIFY 的来源以冻结前快照和逐项迁移映射为准，不能用 Git HEAD 替代含有既有未提交记录的真实来源。当前映射记载 77 条：16 条原未完成、53 条原已完成、8 条原停用。数量只是已核对来源的结果；新增或变化必须重新比对原文摘要。

每条原记录保留稳定条目标识、原文、原状态、证据和真实飞书 GUID 或历史归档入口。相同业务目标复用原任务。飞书写入结果不明时先查询；读回后才冻结。归档工作完成不代表原业务已经验收。公开映射只保存必要来源与关联，不复制私有运行证据。

五个在办任务入口由现有迁移记录覆盖：dashboard-context、config-baseline、dashboard-style、dashboard-hooks、dashboard-native。它们保留原 ID 和有效证据，完成 owner 交接后从最早缺失阶段继续。只有 README 的未开始任务不伪造产品、计划或测试报告。正式门禁应采用 Team 0.2.1 已确认的 README 入口规则。任务 README 与执行、测试证据属于流程产物，不列入本计划的实现源码清单。

### 正式接入与安装前置条件

本项目只增加四个入口：`agent-coops/project.json`、`agent-coops/run.py`、`STATUS.md`、`agent-coops/hooks/pre-commit`。project.json 固定 `workflow_version=0.2.1`、`workflow_source=@installed-team` 和最终程序 `workflow_sha256`；`allowed_roots` 与 `root_files` 仅覆盖本项目已批准路径，不提交机器绝对路径。

run.py 使用 Team 已确认的宿主 loader 入口，不能直接执行项目自行声明的脚本。loader、正式程序和来源登记由 Team 安装管理。Config 不复制私有 workflow 或另建来源白名单。缺少安装入口、版本不符或摘要不符时停止，不能回退执行本仓旧程序来伪装接入成功。

Projects 目录存在双向同步。新 project.json 若先进入该目录，另一端旧 loader 可能立即读取无法识别的保留值。因此按以下顺序执行：

1. 按当前未接入状态的有效规则审查源码，保存 bootstrap 提交与原有检查回执。明确它没有通过尚未安装的新版项目门禁。
2. 由 Team 在两台设备的同步目录外准备正式安装源并安装 loader。验证两端实际版本、来源和旧消费者兼容。工程 worktree 也保留在同步目录外。
3. 双端检查通过后，在本仓隔离 worktree 创建四个入口。产品、架构、开发与测试用各自真实宿主会话绑定和发布；总管确认当前版本。不可通过导出其他人的 session ID 代替真实身份。
4. 对正式候选执行检查，再按本仓 dev/main 与用户验收规则集成。双端 loader 未就绪时，不让新入口进入 Projects 同步目录。

安装受版本控制的 pre-commit 前，再次读取 Git 实际 hook 路径和已有内容。保留后来出现的 hook，不更换 core.hooksPath，不关闭宿主 hook。新增入口只对已接入的当前 checkout 调用受信 runner；其他 checkout 保持原流程。Git 运行状态、真实绑定和安装回执不作为源码提交。

当前已发布且 index 字节一致的阶段产物能否正式入库，由 Team v1.3 的候选检查合同保证。Config 不复制或补丁修改私有门禁。若前置修正尚未部署，则报告该接入阶段阻塞；不能借用其他角色身份绕过。

### 公开范围与后续指南

本仓 manifest 仅保存 Config 相对源码和本地架构资产。跨仓链接只供正本追溯，不进入 assets，不展开 Team 私有正文。公开站点数据、Dashboard overlay 和编辑认证路径保持现有边界。

生产 `site/workflow.html` 不属于本计划 sources。后续真实 Hermes Web 子目标必须先发布自己的设计和精确清单，再修改该文件。本次不得生成替代页面后把真实任务改成重复演示。

自动检查复用现有 unittest、Bash 语法、JSON 与 diff 检查，不新增测试依赖。安装行为只在临时 HOME 中验证。普通文档验证不运行真实安装器、不启动 Dashboard、不生成 site/data.json，也不下载或安装插件。

开发初检结果记录在[执行记录](执行记录.md)。本计划没有重新执行这些实现测试。独立测试须针对最终候选和确认版本复测。真实安装、发布及用户验收尚未由本架构交付证明。
