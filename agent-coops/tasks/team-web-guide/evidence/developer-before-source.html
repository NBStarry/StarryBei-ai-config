CODEX / HERMES · 工作流规范 0.2.0 · 说明基线 2026-10-15

到底有哪些规则？
从一次文件修改说清楚。

这套规范要求 Agent 把任务、计划、执行证据和验收结论放在可追踪的位置。程序能检查部分格式和权限；它不能判断一段“测试通过”的描述是否真实。

行为原则

要求 Agent 怎么做

例如：编辑前重读文件、不改其他任务的内容、没有观察就不能声称验收通过。

写在全局 AGENTS.md。并非每条都有自动拦截。

工具检查

在操作时检查

例如：尝试新增未登记根文件，或执行者改写计划正文，写入前就拒绝。

由 Codex hook 或 Hermes 原生中间件调用固定版本程序。

提交检查

检查即将提交的文件

读取 Git 暂存区，核对目录、任务文档、计划版本及证据格式。

由项目 pre-commit 执行，补充工具检查。

适用范围：本机 Codex 和已启用规范插件的 Hermes 会加载根原则。只有配置了 agent-coops/project.json 的项目才进入这套程序检查。TokenDeck 已接入；未接入项目保留原有流程。

02 / ARCHITECTURE

规则放在哪里，谁负责什么？

本机 Codex 入口

~/.codex/AGENTS.md
链接到配置仓 codex/AGENTS.md

~/.codex/hooks.json
注册四个事件，保留其他 hook

Hermes 原生入口

~/.hermes/plugins/starrybei-workflow
链接到配置仓插件；plugins.enabled 启用它

读取同一份原则，按任务目录检查实际工具调用。独立成员分别安装。

↓ 加载原则，并调用检查入口

共用检查程序

codex/hooks/workflow-hook.py
确定当前项目 → 核对来源、版本和 SHA-256 → 调用 workflow/v0.2.0/workflow.py

↓ 按项目参数检查，不扫描其他任务的全部改动

每个项目的本地记录

project.json：允许目录与固定版本
STATUS.md：状态摘要与任务入口
agent-coops/tasks/任务名/：产品设计、计划、执行记录、证据

本地工程记录

计划保存批准的步骤；执行记录保存命令、结果及局限。Git 保存已提交版本。角色绑定和计划发布回执保存在项目 .git/agent-coops/，不作为公开文件提交。

飞书任务与看板

工作任务保存需求、负责人、期限、开发阶段和最终验收。多维表格从任务清单原生同步，提供需求池、版本拆解、任务管理表、进度看板和人员分配视图。修改状态时操作源任务。

根原则可以长期统一。项目仍固定自己的规范版本和程序摘要。修改共用程序后，旧项目不会静默使用新内容；摘要不匹配会报错。

0.2.0 / FIVE ROLES

新任务如何推进？

打开五角色交互原型、前后对比与返工演示

角色交付物推进条件
总管 coordinator需求、分派、确认、返工及通知回执使用宿主原生子 Agent；保持用户单入口
产品 product产品设计.md、HTML 原型、可观察验收标准总管确认指定版本后进入架构
架构 architect计划.md、架构影响图、开发步骤及源码范围引用已确认产品版本；总管确认后开发
开发 developer实现、自检、执行记录.md引用已确认计划；不得改写业务验收标准
测试 testerevidence/ 中的测试报告、缺陷及复测证据独立会话；覆盖全部适用项及计划源码范围

产物发布使用 publish --artifact product|plan|test --manifest 文件.json。总管使用 confirm 确认版本。正文、本地可视化依赖和实测源码摘要共同约束有效性。设计或源码变化后，旧确认或测试证据失效。

失败后如何返工？

总管将实现问题交开发、技术方案问题交架构、产品或标准问题交产品、测试脚本问题交测试。环境或权限问题由总管在已授权范围内恢复，无法恢复则报告阻塞。设计修订必须重新发布和确认。

初次失败记为第0轮。一次修正和独立复测完成后加1轮。同一验收问题第三轮仍失败时暂停受影响步骤，无关步骤继续；更换角色、版本或编号不能重置轮次。用户决策写入 resume 回执后才能恢复。

用户何时收到通知？

产品确认、架构确认、最终确认后，总管都在当前会话和飞书机器人私聊同步摘要、产物及结论。通知列明设备、宿主、会话名称、Session ID 和产物入口，说明用户从哪里复核。notice 按阶段、版本、渠道记录结果，status 显示待发送项。成功记录不重复发送；失败如实记录并报告，不撤销已完成结论。通知由总管实际发送，门禁不代发消息。

完成条件：全部适用验收项通过、执行记录引用当前计划、全部步骤完成且各有证据、没有未解决问题，总管才可确认最终完成。小修改仍提供修改前后展示和架构影响可视化。用户复核不作为推进条件。

03 / A WORKED EXAMPLE

旧任务示例：把计划中的 S1 标记为完成

  1. SessionStart · 会话开始

    先告诉 Agent 当前规则

    提示读取 STATUS.md，说明当前规范版本和会话角色。它没有替 Agent 完成阅读，也没有证明任务已经完成。

  2. PreToolUse · 调用前

    先检查候选修改，再允许工具写入

    执行者把 - [ ] S1 检查结果 改成 - [x] S1 检查结果。程序检查任务是否绑定给这个会话、计划正文是否保持不变，以及执行记录是否已有 S1 证据。

    允许
    先记录 - 证据 S1：2026-10-13，执行相关检查，结果通过。，再勾选 S1。

    拒绝
    没有证据就勾选 → PLAN_EVIDENCE
    把“检查结果”改成“不用检查” → PLAN_IMMUTABLE

  3. PostToolUse · 调用后

    实际写入必须与候选内容一致

    程序核对文件摘要，并再次验证文档结构。内容与之前的候选不一致时报告 HOOK_CHANGED。它不会自动恢复文件，因为差异可能来自其他执行者。

  4. Stop · 准备结束

    复查尚未清除的检查记录

    如果还有待核对记录，程序再次检查；没有记录则通过。Stop 不运行全部产品测试，不替用户验收，也不自动完成飞书任务。

提交时还有一次检查：即使工作区文件已经修好，如果暂存区仍是旧的错误版本，pre-commit 仍会拒绝。程序检查的是将被提交的内容。

04 / ENFORCED RULES

程序具体拦什么？

展开一条规则，查看条件、例子和处理方式。“工具前”主要指可解析的 Write、Edit、apply_patch；任意 shell 写入不在完整覆盖范围内。

01 · 只能使用项目固定的规范程序 来源与版本

条件：项目存在 project.json。全局入口要求版本格式正确，来源解析到本配置仓对应版本，并且程序 SHA-256 与项目记录一致。

拒绝：把来源改成另一个脚本，或改了共用程序却没有经过版本维护。错误包括 WORKFLOW_SOURCE、WORKFLOW_PIN。

处理：核对实际版本，由规范维护流程更新引用。不要直接删除摘要检查。此检查不禁止用户授权的规范升级。

02 · 文件必须放在项目登记的位置 工具前 / 提交

条件：根文件要在 root_files 中，子目录要在 allowed_roots 中。路径和符号链接不能越出项目。

TokenDeck 示例：Sources/ 是允许的源码目录；随意新增根文件 notes.md 会触发 PATH_DENIED。同样的文件名放到不同项目，结果取决于该项目的参数。

处理：使用项目规定的位置。确实需要新目录时，走已授权的项目规范维护流程。暂存的符号链接变更会触发 PATH_SYMLINK，需要单独审查。

03 · 同一任务使用一组产物 工具前 / 提交
agent-coops/tasks/任务名/
├── 产品设计.md（五角色新任务）
├── 计划.md
├── 执行记录.md
└── evidence/

拒绝：在该目录随意新增第二份任务正文，或直接删除计划、执行记录 → TASK_LAYOUT / TASK_DELETE。项目登记的历史任务目录也不再新增文件 → TASK_LEGACY。

处理：继续更新原记录；必要附件放 evidence。独立目标才创建另一任务。

04 · 任务文档必须有固定四节，且不能空着 工具前 / 提交

五角色任务的产品设计和架构计划使用四节：产品设计、架构设计、验收设计、实施安排。执行记录、测试报告及旧任务仍使用一个一级标题，二级标题依次为：

  1. 目标与范围
  2. 计划与进展
  3. 阻塞与决策
  4. 验收与证据

拒绝：缺一节、顺序不同、额外增加二级标题，或某节没有内容 → DOC_FORMAT / DOC_EMPTY。需要细分时使用三级标题。

05 · 任务必须能从状态入口找到 工具前 / 提交

STATUS.md 不超过80行，并包含当前任务执行记录的路径。执行记录必须链接 计划.md，并包含飞书任务链接格式。

拒绝：只有散落的任务文件，没有入口或计划链接 → TASK_INDEX / TASK_LINK；缺少远端任务链接 → TASK_REMOTE。

边界：程序只检查远端链接格式，不登录飞书验证任务是否存在、身份是否有权限。本地 Markdown 相对链接会检查目标；跨项目链接和计划中的未来路径不作同样检查。

06 · 一个需求入口，由 Agent 安排工作 绑定与委派

用户授权“只向一个入口提需求，其余由 Agent 安排”后，入口整理需求、安排规划和执行、收集证据并汇总结果。用户不需要手动创建开发会话、运行绑定命令或传递交接内容。

0.2.0 的新任务由 coordinator 分派 product、architect、developer、tester。测试必须使用独立宿主会话。总管确认产品、架构和最终结果，三个节点都同步到当前会话及飞书机器人私聊。用户无需回复，流程继续推进。旧任务保留 planner/executor 规则和已有绑定。

拒绝：冒用来源会话 → ROLE_ACTOR；覆盖已有绑定 → ROLE_FIXED；执行者委派、Planner 跨任务委派或发布越权计划 → ROLE_DENIED；委派自身 → ROLE_TARGET。执行者仍不能改写计划。

边界：脚本检查身份、委派关系和冲突；Agent 核对用户授权及任务范围。任意文件或其他 Agent 的声明不算用户授权。委派不是后台调度器，入口仍须使用宿主子 Agent 工具并等待结果。缺少分派能力时明确报告，不要求用户把日常交接当作固定步骤。

07 · 已发布计划的正文不能由执行者改写 工具前 / 提交

执行者可以把合法步骤的 [ ] 改成 [x]。不能删除步骤、改目标或改验收标准；不能把已勾选步骤撤回。

拒绝：直接改写计划 → PLAN_IMMUTABLE；正文没有匹配的发布版本 → PLAN_UNPUBLISHED；撤回勾选 → PLAN_UNCHECK。

处理：将偏差写进执行记录，交独立规划入口在授权范围内发布修订。发布时保留旧版本。勾选状态不计入正文版本摘要。

08 · 勾选步骤前，先写对应证据 工具前 / 提交

步骤使用唯一的 S 编号。执行记录通过 计划版本：正文SHA-256 引用当前计划，并为已勾选步骤保存 - 证据 S1：… 格式的记录。

拒绝：编号重复 → PLAN_STEPS；记录仍引用旧计划 → PLAN_VERSION；缺少证据行 → PLAN_EVIDENCE。

边界：程序不会确认命令真的运行过。证据应写日期、操作、结果和局限，并由执行者和验收者核实。

09 · 步骤没完成，不能写固定的完成结论 工具前 / 提交

执行记录出现 工程结论：已完成 时，程序要求计划步骤全部勾选，否则报 TASK_INCOMPLETE。

边界：当前实现匹配这个固定文本，不理解所有自然语言表述。全部勾选也只说明工程记录满足结构要求，不等于产品验收通过。

10 · 执行任务时不能直接改检查配置 工具前

检查器保护 project.json、项目 run.py、项目 hooks 配置和 pre-commit 文件。直接通过可解析写入工具修改会返回 POLICY_PROTECTED。

处理：如果目标本来就是规范维护，按用户授权执行独立维护流程，并重新验证。不要为了让某一次任务通过而削弱规则。

11 · 写入结果变化时，报告而不自动回退 工具后 / 结束

程序记录解析出的候选路径及内容摘要。工具调用后核对实际结果；不一致则报告 HOOK_CHANGED，成功才清除待查记录。

处理：重新读取文件，确认差异来源。不要把其他执行者的改动覆盖回自己的版本。当前待查记录按会话保存，不是完整的并发事务系统。

12 · 提交检查读取暂存区，不拿工作区代替 Git pre-commit

程序只检查本次暂存路径，并从暂存区读取文件与 project.json。工作区中的修复若没有加入暂存区，不会被当作候选内容。

拒绝：暂存候选缺少 project.json → CONFIG_INDEX；其他目录、格式、计划和证据问题按对应错误返回。

边界：它补充结构检查，不会自动运行 project.json 中列出的全部测试命令，也不证明没有通过其他工具越权操作。

05 / AGENT RESPONSIBILITIES

哪些规则仍要靠 Agent 和人执行？

这些要求写在根原则中。当前程序没有为它们提供完整的自动证明。

原则具体应该做什么程序的实际边界
先读再改开始时读取项目规则、状态、任务；编辑前读取文件当前内容。会话开始只提醒，不追踪每一次阅读。
产品、架构的制作模型制作流程图或交互原型时，优先通过 free-tokens 调用 opus-5.5；调用失败才回退 astra，不得使用其他模型。Agent 记录失败原因和最终模型；astra 也不可用时停止。此为行为要求，当前门禁不检查模型调用。
单一需求入口总管分派四个专业角色、确认设计、安排返工并同步三个确认节点。delegate 检查绑定关系；实际分派和等待由宿主子 Agent 工具完成。
同一目标使用同一入口已有任务继续更新，独立目标才新建。目录检查不判断两个任务的语义是否重复。
保护其他任务只处理本次范围，不接管其他执行者的状态。任务绑定有局部检查；不是全机器访问控制。
优先复用优先使用现有实现、标准库和原生能力。不能自动判断一个依赖或抽象是否必要。
分开报告证据分别说明测试、真实运行和用户验收。检查证据格式，不验证所有陈述真实性。
等待输入时通知需要用户输入且五分钟无回复时，通过飞书机器人私聊通知。四个 hook 没有定时器，也不自动发消息。
表达清楚使用常用词、主动语态；每次最多问一个问题。没有自然语言风格评分或拦截器。

06 / WHEN A CHECK FAILS

遇到拒绝，按这个顺序处理

  1. 读取错误代码和目标路径。先判断是目录、任务归属、计划版本还是证据问题。
  2. 重新读取相关文件。确认当前内容和暂存内容，避免依据旧版本修复。
  3. 修复本次范围内的问题。放回正确目录、补真实证据、更新入口或让规划者发布修订。
  4. 重新运行对应检查。不要关闭 hook，也不要用无关产品测试代替规范检查。

只安装工具入口

bash install.sh --workflow-only

此命令检测已安装的 Codex 和 Hermes，合并规范配置并保存回退快照。重复安装不重复注册；不会自动接入项目。Codex 需在 /hooks 审阅信任后新开会话；Hermes 需重新加载对应进程。

Hermes 独立成员使用其虚拟环境 Python 运行 scripts/install-workflow.py --tool hermes --home ~/.hermes/profiles/成员名，逐个安装。保留成员原有身份和派发规则。回退使用安装输出中的收据：scripts/install-workflow.py --rollback 收据路径。

Hermes 与 Codex 的差异

Hermes 通过 pre_llm_call 注入原则；原生 tool_execution 中间件按任务目录检查 write_file、patch 和 terminal；pre_verify 与会话结束入口核对待查结果。同一会话的受检调用串行执行，避免并发覆盖记录。当前只支持本地终端后端。

手动检查当前任务

python3 agent-coops/run.py check STATUS.md \
  agent-coops/tasks/任务名/计划.md \
  agent-coops/tasks/任务名/执行记录.md

检查即将提交的内容

python3 agent-coops/run.py check --staged

无错误时输出 WORKFLOW_OK。这表示本次规则检查通过，不表示产品已经测试、部署或被用户接受。

07 / SCOPE & EVIDENCE

哪些已经验证，哪些没有？

0.2.0 已通过43项规范隔离测试及30项宿主适配测试。真实独立子 Agent 完成实现返工、架构修订后复测通过，以及三轮失败仅暂停受影响步骤。手动候选检查验证局部暂停，不等同于真实宿主 hook 拦截。用户实际业务试用待确认。远端 Hermes 本轮未升级。

  • 历史宿主证据：旧版安装、回退、规则与宿主适配隔离测试通过；Hermes 原生分发器验证通过；Codex 和 Hermes 真实模型会话均完成合法写入，并拒绝违规根文件。这些旧版结果不替代0.2.0业务验收。
  • 未覆盖全部写入：任意 shell、解释器或 MCP 内部修改无法完整还原。Git 检查补充候选内容验证，但不构成操作系统权限隔离。
  • 没有全局完成认证：Stop 只处理待查记录，不扫描全部任务、不完成飞书任务、不自动提交或发布。
